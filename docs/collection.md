# 采集框架

版本：草案 2026-10-16（修订：双轴 + 明暗内容分工）  
目的：先定「收什么、从哪收、怎么过审」，再扩数据和脚本。  
相关：`CONTRIBUTING.md`（投稿规则）、`docs/design.md`（产品体验）、`src/data/sources.yaml`（信源池）。

---

## 1. 结构：主轴编年 + 副轴乐子

```text
主轴（编年，保持干净）
  明面：厂商怎么宣传模型能力
  暗面：用户实际反馈与翻车
        ↕ 关联（明或暗都可挂乐子）
副轴（乐子，默认开，视觉更弱，随主轴同步看）
  梗图 / 二创 / 八卦 / 迷因
```

| 轴 | 代号 | 用户感知 | 入库门槛 |
|---|---|---|---|
| 主轴 · 编年 | `chronicle` | 明暗对照的时间线，卡片是事实条目 | 严：来源、严重程度（暗）、事后、`verified` |
| 副轴 · 乐子 | `fun` | 梗图与传播向内容；**不进主轴卡片流** | 宽：标明乐子；可展示 ≠ 事实已核实 |

### 1.1 明面 / 暗面收什么（编年分工）· 已定稿

| 面 | 收 | 不收（改走乐子或丢掉） |
|---|---|---|
| **明面** | 厂商发布、官方能力宣称、评测里厂商主推的能力点、开放权重与产品节点 | 纯梗图、二创、吃瓜截图 |
| **暗面** | 用户实际反馈、公开事故、监管与诉讼、可核对的翻车与事后 | 无来源的嘴炮；人身攻击 |

对照关系不变：暗史尽量 `related` 到某次明史发布。明暗都是**主轴节点**，翻面逻辑保持现有两仪。

### 1.2 乐子轴 · 已定稿

- **梗图属于乐子**，不再作为编年条目的主内容字段长期存放（现有 `events[].memes` 迁到 `fun/`，编年卡片只保留「相关乐子」入口）。
- 乐子可由**明面或暗面**关联（`related` 指向任意编年 id，不限 light）。
- 乐子是**独立副轴**：与主轴按日期对齐、一同滚动；开关「显示乐子」**默认开**，视觉弱于主轴，**主轴保持干净**。
- 主轴卡片上不直接铺梗图；**点击进入 card 详情**（或展开详情区）再看相关乐子 / 梗图。
- 乐子不参与严重程度点大小；不占用暗史 1–5 标尺；分享文案不写成「核实事故」。

### 1.3 什么进乐子、什么仍不收

| 进乐子 | 仍不收 |
|---|---|
| 二创梗图、迷因、表情包 | 针对个人的攻击、人肉、仇恨 |
| 厂商 / 模型相关八卦与传播向趣闻 | 伪造对话冒充编年证据 |
| 挂在某次发布或某次翻车上的社区二创 | 纯广告、无事件内核的软文 |

编年里的「误用 / 自披露」仍按 `CONTRIBUTING.md`（带标签与严重程度上限）。平台误操作不进暗史；若有传播价值进乐子。

## 2. 采集清单（字段）

### 2.1 编年 · 主轴（`src/data/events/`）

| 字段 | 明史 | 暗史 | 说明 |
|---|---|---|---|
| `date` | 必填 | 必填 | 事件发生日 |
| `side` | `light` | `dark` | 明=厂商宣称；暗=用户反馈/翻车 |
| `vendor` / `model` | 必填 | 必填 | |
| `title` / `summary` | 必填 | 必填 | 明史可写能力宣称（须有出处）；暗史写可核对事实 |
| `category` | 建议 | 建议 | 见 §3 |
| `severity` | 禁止 | 必填 1–5 | |
| `related` | 禁止 | 建议 | 暗→明的发布对照 |
| `response` | 可选 | 强烈建议 | 厂商 / 监管 / 法院事后动作 |
| `sources` | ≥1 一级，建议 archive | ≥2 源，或 1 一级 + archive | 见 §4 |
| `verified` | 默认 false | 默认 false | 仅人工复核后改 true |
| `memes` | **废弃（迁出）** | **废弃（迁出）** | 改由乐子轴承载；卡片详情反查 `fun.related` |

### 2.2 乐子 · 副轴（`src/data/fun/`）· 已定稿

**存放**：独立目录，独立 collection。  
**与主轴关系**：按 `date` 对齐副轴；用 `related`（可多值）挂到明或暗的编年 id；主轴详情页反查展示。

| 字段 | 要求 | 说明 |
|---|---|---|
| `date` | 必填 | 传播高峰日或可考日期 |
| `title` / `summary` | 必填 | 语气可轻松，不捏造 |
| `vendor` / `model` | 建议 | 方便筛选 |
| `sources` | ≥1 线索 | 社交平台须写明 |
| `fun_kind` | 必填 | `meme` / `gossip` / `remix` / `rumor` |
| `related` | 建议 | **字符串或数组**，指向编年 id（明或暗皆可） |
| `images` | 梗图类必填 | 文件在 `public/memes/<fun-id>/`；可事后人工补 |
| `listed` | 默认 false | 可展示；不用 `verified`，避免与编年混淆 |
| `nsfw` / `attack` | 默认 false | 人身攻击直接拒绝 |

**第一批**：把现有编年下的梗图迁成乐子条目并 `related` 回原事件；同时收独立八卦；之后允许人工补图。

**id**：强制 `fun-` 前缀（或 collection 路径保证与 events 不撞 `#hash`）。

## 3. 编年类目（`category`）

用于检索与统计，可多选。当前仓库里「发布」过多，后续收敛到下面集合：

| 类目 | 主要用于 |
|---|---|
| `发布` | 上线、开放权重、默认模型切换 |
| `幻觉` | 事实性错误造成公开事故 |
| `对齐` | 迎合、越狱、红队披露 |
| `人格` | 角色崩坏、不当关系表述 |
| `隐私` | 泄露、越权、数据外流 |
| `监管` | 禁令、调查、罚款 |
| `版权` | 诉讼、训练数据争议 |
| `偏见` | 刻板印象、政治正确翻车 |
| `审查` | 审查策略本身成为事件 |
| `泄露` | 权重 / 提示词 / 内部文档流出 |
| `误用` | 用户误用（严重程度 ≤3） |
| `自披露` | 厂商主动披露（严重程度 ≤2） |

## 4. 信源与流水线

### 4.1 原则

```text
信源池 → 发现线索 → 起草（draft）→ 模型核对（review）→ 人工复核 → verified / 上架乐子
```

- **信源池**是白名单与巡视清单，不是自动信任。
- **模型核对**只产出建议；`verified` 只能人工改。
- **人工审核录入**：新信源先 `status: pending`，维护者改成 `approved` 后才进入常规巡视。

### 4.2 信源等级

| 等级 | 含义 | 例子 |
|---|---|---|
| `tier: 1` | 一级 / 原文 | 厂商博客、系统卡、监管与法院原文、论文 |
| `tier: 2` | 署名媒体 | 路透、MIT Tech Review、财新、晚点等 |
| `tier: 3` | 线索 | AI Incident Database、AIAAIC、行业通讯；社交平台只作发现 |

编年：至少 1 个 tier 1，或 2 个 tier 2；暗史优先「tier 1 + archive」。  
乐子：允许仅 tier 3，但卡片上要能点开来源。

### 4.3 现有脚本怎么接

| 步骤 | 现状 | 下一步 |
|---|---|---|
| 发现 | `pnpm collect` | 扫 AIHOT 和信源池里带 `feed` 的源，输出 `reports/collect/` |
| 排队 | `pnpm triage` | AI 粗分为编年 / 乐子 / 丢弃；编年每天最多 5 个 Issue，乐子最多 10 个。不改 `verified` |
| 收 | Issue 评论 `/收` | 仅维护者。云端 `draft` 开 PR，同 job 跑 `review`。`/丢` 关 Issue。不改 `verified` |
| 起草 | `pnpm draft <url>` | 识别信源是否在池内，自动填 `tier` / 建议 `lane` |
| 模型核对 | `pnpm review` | 编年严查事实；乐子只查「是否人身攻击 / 是否明显伪造」 |
| 人工复核 | 改 YAML + `verified` | 信源录入走 `sources.yaml` 的 pending → approved |
| 存档 | draft 已尝试 archive.org | 编年入库前尽量补齐 `archive` |

### 4.4 信源人工审核录入（后续）

1. Issue / 表单提交候选信源（名称、URL、类型、理由）。
2. 写入 `src/data/sources.yaml`，`status: pending`。
3. 维护者核对域名、是否一手、是否稳定更新 → `approved` 或 `rejected`。
4. 只有 `approved` 进入巡视脚本与 draft 的「可信提示」。

## 7. 实施顺序

一人维护时，先把发现结果变成可处理的队列。`fun` collection、副轴 UI、梗图迁徙暂缓，避免在还没有稳定质检节奏时扩展示层。

1. ~~定稿框架 + 信源池 + 双轴关系~~
2. **当前：收集排队。** 每天 `collect` → `triage` 粗分 → 限量开 Issue（编年 5、乐子 10）。`verified` 只能人工改。
3. 按周处理 `候选/编年`：Issue 评论 `/收`（待定用 `/收 明` 或 `/收 暗`）→ 云端起草并开 PR（同 job 审查 + check）→ 人工改 `verified` → 合并。`/丢` 只关候选 Issue。
4. 暂缓：`fun` collection、副轴 UI、编年详情里的梗图、`events[].memes` 迁出。
5. 之后再按信源池补一手 `feed`，以及明面能力点、暗面反馈的正文。

硬约束：

- 自动产物一律是候选，禁止脚本或 CI 把 `verified` 改成 `true`。
- 超出限额的线索只留在 `reports/collect/`。
- 勘误是事后通道，不替代入库质检。

## 8. 可行性验证（修订）

### 8.1 原阻塞点：已由「副轴」化解

乐子**不再争夺**主轴的 `light|dark` 列位：

| 机制 | 新落点 |
|---|---|
| 主轴两栏 / 翻面 | 只服务编年，不动 |
| 副轴 | 独立轨道（例如主轴外侧一条弱轨，或年份旁的旁注点），`data-fun` 开关 |
| 统计 | 仍「明史 N · 暗处 M」；乐子另计「乐子 K」或不进主统计 |
| 定位条 | 主刻度=编年；乐子刻度更淡更短，或开关关闭时不画 |
| 详情 | 点击主轴 card → 详情区列出 `related` 反查到的乐子 / 梗图 |
| `related` | 编年暗→明不变；乐子→编年（明或暗）另校验 |

这比「乐子当第三种主轴节点」更贴你的定稿，也更好实现。

### 8.2 仍要注意

1. **副轴怎么「随着主轴看」**  
   按日期对齐：同一时段的乐子画在主轴节点旁，或详情内展示缩略；整页同步滚动即可，不必第二套 scroll container。若做成真正第二条 sticky 轴，要防手机挤爆——**手机建议默认收起副轴，只保留详情里的梗图入口**。

2. **现有 `memes` 迁移**  
   已有事件带梗图（如 sycophancy、sydney）。需一次性脚本：生成 `fun-*` YAML + 移动 `public/memes/` 路径 + 清空编年 `memes`（或构建期兼容一季后删除）。

3. **明面内容转型**  
   今日明史多是「发布了」一句。按新分工应逐步补：**宣称了哪些能力**（须带来源句）。暗史则明确优先「用户侧反馈」类来源（论坛、工单公开信、署名体验），不只是监管通稿。

4. **详情交互尚未存在**  
   现在卡片即列表项，没有独立详情页/抽屉。要「点进 card 看梗图」需加一层 UI（锚点展开、drawer 或 `/event/[id]`）。这是副轴方案的前置工程，工作量中等，但比改翻面逻辑安全。

5. **其余**（id 前缀、`listed`、信源门槛进校验、池子暂无自动巡视）仍成立，见上一版分析。

### 8.3 验证结论

| 判断 | 内容 |
|---|---|
| 可落实 | 双轴模型与现有明暗翻面**不冲突**；信源池与 review 流水线可并行 |
| 当前阶段 | 收集排队：定时 collect、triage 开候选 Issue、每周人工点头。fun UI 暂缓 |
| 文档债 | 更新 `design.md` / `CONTRIBUTING.md`：梗图归乐子；明=宣称，暗=反馈 |

**结论：方案可落实。** 原先 §8.1 的 A/B/C 作废，以「主轴干净 + 副轴乐子 + 详情看梗图」为准。
